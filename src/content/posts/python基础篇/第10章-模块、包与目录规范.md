## 10.1 什么是模块

**模块（module）是一系列功能的集合体。** 一个 `.py` 文件就是一个模块，文件名就是模块名（去掉 `.py`）。
```python
# 文件: module.py
def func1():
    print('我是func1')

def func2():
    print('我是func2')
```

`module.py` 这个文件就是模块 `module`。
模块分三类：

| 类别 | 说明 |
|---|---|
| 内置模块 | Python 自带，随解释器一起安装，如 `time`、`os`，不用考虑放哪里 |
| 第三方模块 | 别人写好的功能，下载安装后直接用，如 `requests`、`pymysql` |
| 自定义模块 | 自己写的，写完要自己决定放在哪里 |

**为什么要用模块：避免代码冗余。**

- 以前：同一个文件里有重复功能 → 定义成函数
- 现在：同样的功能要在不同 `.py` 文件里用 → 把它们存进一个模块，其他文件导入即可


:::note[补充]
也有人把这种组织形式叫"库"（library），并说"库是包的集合、包是文件的集合、文件是功能的集合"。名字不必纠结，**区分清楚模块和包就好**。
:::

## 10.2 模块的导入方式

导入模块用关键字 `import`，后面跟**模块名**，**不要加 `.py`**。
```python
# 文件: module.py
print('我是module')        # 模块文件也是 Python 文件，可以写任何代码
name = '梦泪'

def func1():
    print('我是func1')

def func2():
    print('我是func2')
```

```python
# 文件: run.py（与 module.py 在同一文件夹）

import module
import module
import module
# 输出（只打印一次）:
# 我是module
```

对 `run.py` 来说，`module` 就是它里面的一个名字，指向 `module.py` 那边的内容。
**首次导入模块时发生三件事**：

1. 立即执行一遍模块文件
2. 创建模块的名称空间，把运行中产生的名字放进去
3. 在当前文件中创建名字 `module`，指向模块的名称空间

**之后的重复导入只引用首次导入的结果，不会重复执行。**

### 10.2.1 `from ... import`：不写前缀的导入

`import module` 后，每次用功能都要加 `module.` 前缀。想不加前缀，就用 `from 模块名 import 名字`：

```python
# 文件: run.py
from module import name, func1, func2

print(name)     # 输出: 梦泪
func1()         # 输出: 我是func1
func2()         # 输出: 我是func2
```

**两种写法的区别**：

| 写法 | 当前名称空间里产生的名字 | 指向 |
|---|---|---|
| `import module` | `module` | 模块的**名称空间** |
| `from module import name` | `name`（不会有 `module`） | 模块名称空间里 `name` 对应的**值** |

**缺点**：`from` 导入的名字直接指向值，一旦当前文件和模块里的名字重名，就再也没法用原来的名字访问模块里的值了。
```python
# 文件: run.py
from module import name, get

name = '李白'    # 改的是当前名称空间的 name
get()            # 输出: 梦泪（get 找的始终是 module 名称空间里的 name）
```

### 10.2.2 导入多个模块的规范

```python
# 不推荐：一行导入多个
import time, os

# 推荐：一行一个
import time
import os
```

**导入顺序**：内置模块 → 第三方模块 → 自定义模块。不按顺序也能运行，但按顺序更规范、别人读代码更清晰，**千万别混在一起**。
```python
# 内置模块
import time
import os

# 第三方模块（需先安装，这里仅示意）
# import pymysql
# import requests

# 自定义模块
# import module
```

### 10.2.3 用 `as` 起别名

```python
import datetime as dt

print(dt.date.today())   # 输出: 2026-10-13
```

模块名较长时起个短别名，避免到处写一长串前缀。别名要有标识性，让人大概能看出是哪个模块。
### 10.2.4 模块命名规范

自定义模块名用**纯小写加下划线**，这是 Python 3 的规范。Python 2 里风格较乱，有些模块用驼峰体，到 Python 3 全部改成了小写。
```python
import socketserver   # Python 2 中叫 SocketServer
import queue          # Python 2 中叫 Queue
```

### 10.2.5 在函数内部导入

模块名属于函数的**局部名称空间**，函数外访问不到。
```python
def func():
    import random
    return random.randint(1, 10)

print(func())     # 输出: 7
# print(random)   # 会报错: NameError
```

## 10.3 模块只被执行一次与模块名称空间

**结论：模块代码只在首次导入时执行一次，之后再导入都直接用已存在的名称空间。**

原因：已导入的模块保存在 `sys.modules` 字典里，导入时先从这里找，找到就直接用。

:::note[补充]
单纯 `del json` 只删除了当前文件里的名字，模块对象仍在 `sys.modules` 中，再次 `import` 也不会重新执行。

```python
import sys
import json

del json                         # 只删掉当前文件里的名字 json
print('json' in sys.modules)     # 输出: True，模块对象还在内存里
import json                      # 不会重新执行，直接从 sys.modules 取
print(json.dumps([1, 2]))        # 输出: [1, 2]
```
:::


**名称空间隔离**：当前文件和模块的名称空间完全隔开，即使重名也不冲突，访问模块里的名字必须加 `module.` 前缀。
```python
# 文件: run.py
x = 10
y = 20
import module

print(module.name)   # 输出: 梦泪
module.func1()       # 输出: 我是func1
module.func2()       # 输出: 我是func2
```

**名称空间的查找顺序在定义阶段就确定了。**

```python
# 文件: module.py
name = '梦泪'

def func1():
    print(name)          # 找 module 自己的 name

def func2():
    global name
    name = '周杰伦'       # 改 module 自己的 name

def get():
    print(name)
```

```python
# 文件: run.py
import module

name = '李白'
module.func1()       # 输出: 梦泪（不会去 run.py 找 name）
module.func2()
print(name)          # 输出: 李白（run.py 的 name 不受影响）
print(module.name)   # 输出: 周杰伦（module 的 name 被改了）
module.get()         # 输出: 周杰伦
```


:::warning[注意]
函数找名字的顺序是：局部 → 全局 → 内置，找不到就报错，**永远不会去别的文件里找**。所以无论查找还是修改，操作的都是模块本身，**和调用位置无关**。
:::

**名称空间回收时机**：

- 直接运行的文件：代码跑完，名称空间就回收
- 被导入的模块：`run.py` 里的 `module` 还引用着它，要等 `run.py` 跑完才回收

回收顺序：执行文件运行结束 → 执行文件名称空间回收 → 模块名称空间引用计数归零 → 模块名称空间回收。
## 10.4 `__name__` 与模块编写规范

模块写出来是给别人导入的，但它本身也能直接运行。调试时会想调用 `func1()`、`func2()` 看看有没有 bug，可一旦写死在里面，别人导入时测试代码也会跟着执行。
Python 为每个文件内置了属性 `__name__`：

- **直接运行**该文件时：`__name__` 为 `'__main__'`
- **作为模块被导入**时：`__name__` 为**模块名**

```python
# 文件: module.py
print('module.py 的 __name__:', __name__)

# 直接运行 module.py → 输出: module.py 的 __name__: __main__
# 在 run.py 里 import module → 输出: module.py 的 __name__: module
```

利用它就能把测试代码保护起来：

```python
# 文件: module.py
def func1():
    print('我是func1')

def func2():
    print('我是func2')

if __name__ == '__main__':     # 文件被直接运行时才执行
    func1()
    func2()
```


:::tip[技巧]
在 PyCharm 中输入 `main` 再回车，会自动生成 `if __name__ == '__main__':`——这是内置的实时模板。
:::

**规范的模块按以下顺序编写**：

```python
#!/usr/bin/env python3
"""
文档注释：描述这个模块的功能。
例如：本模块提供 func1、func2 两个示例功能。
"""

# 导入模块
import sys
import os

# 定义全局变量（如非必须，最好定义成局部变量）
name = '梦泪'


# 定义类（需要写注释）
class Foo:
    """类的注释"""
    pass


# 定义函数（需要写注释）
def func1():
    """func1的功能说明"""
    print('我是func1')


def func2():
    """func2的功能说明"""
    print('我是func2')


# 主程序：作为脚本运行或测试本模块时执行
if __name__ == '__main__':
    func1()
    func2()
```

逐项说明：

1. `#!/usr/bin/env python3`：只在 Unix 类环境下有效，作用是可以直接用文件名运行；Windows 下可忽略
2. 文档注释：描述模块功能，可用 `模块名.__doc__` 查看
3. 导入模块
4. 定义全局变量：**尽量少用**，能定义成局部变量就定义成局部变量，让各功能相互独立
5. 定义类（写注释）
6. 定义函数（写注释）
7. `if __name__ == '__main__':` 下写主程序或测试代码

不按这个顺序写也不会出错，但按顺序更规范。课堂上没写 `__all__` 也能用，因为默认 `import *` 会导入所有**不以下划线开头**的名字。
### 10.4.1 循环导入

**循环导入**：模块 `a` 导入 `b`，`b` 又导入 `a`（直接或间接）。
```python
# 文件: a.py
import b
print(b.y)
x = 1
```

```python
# 文件: b.py
import a
print(a.x)
y = 2
```

```python
# 文件: main.py
import a
```

执行 `import a` 时：a 导入 b → b 又导入 a → b 想要 `a.x`，但 `x = 1` 还没执行 → 报错 `AttributeError`。
**两种应急措施**：

方法一，把定义往上提：

```python
# 文件: a.py
x = 1           # 先定义
import b
print(b.y)
```

方法二，把用到的代码缩进到函数里（函数定义阶段不执行代码，等调用时名字早已产生）：

```python
# 文件: a.py
import b
x = 1

def func():
    print(b.y)  # 调用时才去找 b.y
```


:::warning[注意]
这些都只是补救措施，本质是"屎上雕花"——逻辑本身就有问题。**根本办法是重新组织代码**：把两个模块都需要的公共部分抽到第三个模块，让它们都去导入这个公共模块。
:::

## 10.5 什么是包

**包（package）是含有 `__init__.py` 文件的文件夹，也是模块的一种。**

在 PyCharm 中右键 → New：

- `Python File`：新建 Python 文件
- `Directory`：新建普通文件夹
- `Python Package`：新建 Python 包（自动创建 `__init__.py`）

```text
project/
├── run.py
└── pack/              <- 包
    └── __init__.py    <- 空文件
```

自己建一个文件夹再手动放一个 `__init__.py`，效果完全一样。
包既然是模块的一种，前面学的 `import`、`from ... import`、查找顺序**同样适用于包**：

```python
import pack     # 正常运行
```

**导包和导模块的流程一样**：

1. 创建一个名称空间
2. 执行一个 `.py` 文件，把执行中产生的名字放进名称空间
3. 在当前文件中创建名字，指向这个名称空间

包不是 `.py` 文件，那"执行"的是谁？就是 `__init__.py`。

:::note[补充]
Python 3 中包里没有 `__init__.py` 也不会报错（称为"命名空间包" namespace package），只是点不出任何名字；Python 2 中必须有 `__init__.py`。
:::

## 10.6 导包就是导 `__init__.py`

```python
# 文件: pack/__init__.py
print('我是init')
name = '梦泪'

def func():
    print('init里的函数')
```

```python
# 文件: run.py
import pack

print(pack.name)   # 输出: 梦泪
pack.func()        # 输出: init里的函数
```

当前名称空间里的 `pack` 名字，指向的就是 `__init__.py` 的名称空间。也就是说，**导入一个文件夹，拿到的只是 `__init__.py` 里的名字**。
## 10.7 包的意义：游戏模块升级场景

**类比**：包就像商场的一个招牌门面——顾客从招牌进门就能买到所有东西，不管里面换了多少个柜台、怎么重新布局，顾客认的还是这个招牌。
假设你做游戏开发，写了一个模块 `game.py`（`chat` 代表你写的 10 个功能）发布到网上：

```python
# 文件: game.py（初版，模块设计者）
def chat():
    print('聊天功能')
```

使用者下载后直接用：

```python
# 文件: run.py（模块使用者）
import game

game.chat()     # 输出: 聊天功能
```

功能越来越多（背包 `knapsack`、地图 `map`……），全塞在一个文件里又乱又难维护。于是你把功能拆成三个文件，删掉 `game.py`：

```text
chat.py
knapsack.py
map.py
```

设计者清爽了，使用者却懵了：**原来的代码 `import game` 全都用不了了。**

这里有一条原则：

- 对设计者：功能可以任意拆分，便于维护
- 对使用者：拿到手的**只能是一个"模块"**，用法和模块名都不应该变化

**解决方案：包。** 新建包 `game`（与原模块同名），把三个文件放进去：

```text
project/
├── run.py              <- 执行文件（使用者）
└── game/               <- 包（设计者发布的"模块"）
    ├── __init__.py
    ├── chat.py         <- def chat(): ...
    ├── knapsack.py     <- def knapsack(): ...
    └── map.py          <- def map(): ...
```

再在 `__init__.py` 里把三个子模块的功能汇总进来：

```python
# 文件: game/__init__.py
from game.chat import chat
from game.knapsack import knapsack
from game.map import map
```

使用者的代码一行都不用改：

```python
# 文件: run.py
import game

game.chat()          # 输出: 聊天功能
game.knapsack()      # 输出: 背包功能
game.map()           # 输出: 地图功能
```

**这就是包的意义**：设计者把代码拆分、组织清晰，同时**对使用者屏蔽内部变化**，用法保持不变。
## 10.8 绝对导入与 sys.path

在 `__init__.py` 里为什么写 `from game.chat import chat`，而不写 `from chat import chat`？

**结论：被导入模块的 `sys.path` 参照的是执行文件的 `sys.path`。**

```python
# 文件: run.py
import sys
print(sys.path[0])   # 执行文件所在文件夹，即 project
import game
```

```python
# 文件: game/__init__.py
import sys
print(sys.path[0])   # 打印的仍然是 project
```

两处打印的都是 `project`——两个 `sys.path` 根本就是同一个列表。`chat.py` 和 `__init__.py` 虽然在同一目录，但找模块要按 `sys.path`，而 `sys.path[0]`（即 `project`）下面只有 `game` 没有 `chat`，所以必须从 `game` 开始找。
**绝对导入（absolute import）**：以顶级包为起始位置导入，参照执行文件的 `sys.path`。
```python
# 文件: game/__init__.py（绝对导入）
from game.chat import chat
from game.knapsack import knapsack
from game.map import map
```

**前提**：使用者要把包所在的路径加入 `sys.path`。包放在执行文件同级目录可以，放到别的文件夹（如 `mm`）时要先加路径：

```python
# 文件: run.py
import sys

sys.path.append(r'D:\xxx\mm')   # 换成 game 包实际所在的文件夹

import game
game.chat()                     # 输出: 聊天功能
```

对设计者来说，他知道使用者一定会保证 `game` 在 `sys.path` 里，所以在包内以 `game` 为起点一定能找到——这就是绝对导入。
**模块的查找顺序**（`import` 和 `from` 都一样）：

1. **先从内存找**：已导入的模块记录在 `sys.modules` 中（更精确地说，还会先检查编译进解释器的内置模块，如 `sys`、`time`）
2. **内存没有，去硬盘找**：按 `sys.path` 中的路径从前往后依次查找

都找不到就报 `ModuleNotFoundError: No module named 'xxx'`。
```python
import sys
print(sys.path)
# 输出示例（PyCharm 中运行）:
# ['D:\\project\\28-package',                   <- 执行文件所在文件夹
#  'D:\\project',                                <- PyCharm 打开的项目文件夹
#  'D:\\Python\\Python313\\python313.zip',
#  'D:\\Python\\Python313\\Lib',                <- 标准库
#  'D:\\Python\\Python313\\Lib\\site-packages'] <- 第三方模块
```

- **第一个路径永远是执行文件所在的文件夹**
- 第二个路径（项目文件夹）是 PyCharm 自动加的；在 cmd 里用 `python 绝对路径` 运行就没有这一项。上线运行时不会有 PyCharm，**所以写代码时应当假设它不存在**
- `.zip` 压缩包对 Python 来说也是文件夹，当文件夹看待即可
- `Lib` 是标准库，`Lib\site-packages` 是第三方模块的安装位置

**导入任意目录下的模块**：`sys.path` 只是列表，用 `append` 把模块所在文件夹的绝对路径加进去即可。
```python
# 文件: run.py
import sys

sys.path.append(r'D:\project\mm')   # module.py 所在文件夹

import module
module.get()
```


:::warning[注意]
用 `append` 加到末尾，不要用 `insert` 破坏原有顺序；这样添加只是**临时有效**，程序结束就失效。另外，**自己的文件不要和标准库模块重名**（如 `random.py`、`json.py`），否则导入的是你自己的文件。

PyCharm 可能仍给 `import module` 标红色波浪线，那是路径动态添加、它识别不了，不是代码问题，运行不会报错。
:::

路径写死不利于移植，更好的方案是用 `__file__` 动态计算：

```python
import os
import sys

BASE_DIR = os.path.dirname(os.path.abspath(__file__))
sys.path.append(os.path.join(BASE_DIR, 'mm'))
```

## 10.9 点的左边必须是包

**重要原则：导入时带点的，点的左边都必须是包。**

```python
from game.chat import chat   # game 是包
from a.b.c.d import f        # a、b、c 都是包，d 是模块，f 是名字
```

示例：在 `game` 下再建一个子包 `GG`，里面有子模块 `pay.py`：

```text
game/
├── __init__.py
├── chat.py
├── knapsack.py
├── map.py
└── GG/                 <- 子包
    ├── __init__.py
    └── pay.py          <- brilliant = 520
```

```python
# 文件: game/GG/pay.py
brilliant = 520
```

使用者只想 `from game import brilliant`，不想关心它嵌套了多少层。那就得在 `game/__init__.py` 里把它拿出来：

```python
# 文件: game/__init__.py
from game.chat import chat
from game.knapsack import knapsack
from game.map import map
from game.GG.pay import brilliant   # 点左边的 game、GG 都是包，符合原则
```

```python
# 文件: run.py
from game import brilliant

print(brilliant)   # 输出: 520
```

既可以 `import` 包，也可以 `from ... import` 包里的名字：

```python
# 文件: run.py
from game import chat, knapsack, map

chat()
knapsack()
map()
```

**`import` 也可以用点，但要注意**：

```python
# 文件: run.py
import game.chat

# chat()          # 会报错: NameError: name 'chat' is not defined
game.chat()       # 正确，输出: 聊天功能
```

`import` 后面跟的名字是一个**整体**，使用时必须带完整前缀，前缀再长也得带。所以这种写法**不推荐**。

:::note[补充]
`from ... import` 中，`import` 后面不能带点。`from game import GG.pay` 是语法错误，应写成 `from game.GG import pay`。
:::

## 10.10 相对导入

**相对导入（relative import）**：以当前文件所在文件夹为参照。
| 写法 | 含义 |
|---|---|
| `.` | 当前文件所在文件夹 |
| `..` | 上一层文件夹 |
| `...` | 再上一层（以此类推） |

把 `game/__init__.py` 改成相对导入，`.` 就代表 `__init__.py` 所在的 `game`：

```python
# 文件: game/__init__.py（改用相对导入）
from .chat import chat
from .knapsack import knapsack
from .map import map
from .GG.pay import brilliant
```

**`..` 的用法**：给 `pay.py` 加一个交易功能 `sell`，它要用到上一层的 `chat`，所以用 `..` 跳到 `game`，`GG` 里再往上就跳出顶级包了：

```python
# 文件: game/GG/pay.py
from ..chat import chat     # .. 表示上一层文件夹（game）

brilliant = 520

def sell():
    print('交易功能')
    chat()
```

再在 `game/__init__.py` 里把 `sell` 也导出来：

```python
# 文件: game/__init__.py
from .chat import chat
from .knapsack import knapsack
from .map import map
from .GG.pay import brilliant, sell
```

```python
# 文件: run.py
from game import sell

sell()
# 输出:
# 交易功能
# 聊天功能
```

**为什么包内推荐相对导入**：

1. 包内容、子包越来越多时，绝对导入要写很长的层级，相对导入方便得多
2. 如果包名变了（如 `game1` 升级成 `game2`），包内所有绝对导入都得改；相对导入不存在这个问题

**绝对导入 vs 相对导入**：

| | 绝对导入 | 相对导入 |
|---|---|---|
| 参照 | 执行文件的 `sys.path` | 当前文件所在文件夹 |
| 限制 | 无限制 | 不能跳出顶级包，仅限包内模块之间 |


:::warning[注意]
使用相对导入的文件不能直接作为执行文件运行，否则报 `ImportError: attempted relative import with no known parent package`；相对导入只能用 `from . import xxx` 形式，不能写 `import .xxx`。
:::

## 10.11 软件目录规范

目录规范**不是固定死的**：不同公司、不同项目可能略有差异，文件夹名字也可能不同，但该有的目录一个都不会少。不遵守也能跑，但它是从小白迈向专业程序员很重要的一步。
假设项目名叫 `catalog`（新建项目本质就是新建一个文件夹）：

```text
catalog/                    <- 项目根目录
├── bin/                    <- 可执行文件
│   ├── run.py              <- 程序的启动文件（入口）
│   └── setup.py            <- 安装、部署、打包脚本（暂时用不到）
├── conf/                   <- 配置文件
│   └── settings.py         <- 用户可自己配置的内容
├── lib/                    <- 程序中多处都要用的常用功能
├── core/                   <- 核心代码逻辑
├── log/                    <- 项目日志
├── db/                     <- 数据库相关操作
│   └── db_handle.py        <- 增删改查等数据操作功能
├── api/                    <- 接口（暂时用不到）
├── requirements.txt        <- 外部依赖（文件名不可改）
└── README.md               <- 软件说明（一定要有）
```

各部分说明：

- **bin**：放启动文件 `run.py`，它只负责启动程序，核心逻辑写在 `core` 里由它调用，这样结构更清晰。如果文件很少，**可以不要 bin 文件夹**，把启动文件直接放项目根目录
- **conf**：用户自定义配置，比如重要数据的存放路径
- **lib**：程序多处用到的公共功能
- **core**：核心代码逻辑
- **log**：存放项目日志
- **db**：数据库操作功能。比如用户注册要把信息写进数据库，程序任何地方想操作数据库都直接调这里的功能
- **requirements.txt**：项目用到的第三方模块及版本，每行一个，如 `requests==2.32.3`。别人执行 `pip install -r requirements.txt` 就能一次装好
- **README.md**：对软件的解释说明，如功能、用法、官网地址等

## 10.12 分层编写核心逻辑

目录建好后先写核心逻辑。在 `core/core.py` 中写电子钱包的登录、注册、充值、转账功能（不做提现），用字符串的 `center` 方法居中打印更美观。
用一个**函数字典**组织功能，避免写一长串 `if` 判断。字典的值是小元组 `(功能名, 函数)`；退出不需要自己写函数，直接用内置的 `exit`——**注意不加括号**，存的是函数本身。
```python
# 文件: catalog/core/core.py（第一版）

def login():
    print('执行登录功能'.center(30, '*'))

def register():
    print('执行注册功能'.center(30, '*'))

def recharge():
    print('执行充值功能'.center(30, '*'))

def transfer():
    print('执行转账功能'.center(30, '*'))

# 函数字典：编号 -> (功能名, 函数)
func_dic = {
    '0': ('退出', exit),      # exit 不加括号，存放函数本身
    '1': ('登录', login),
    '2': ('注册', register),
    '3': ('充值', recharge),
    '4': ('转账', transfer),
}
```

"输入有误"属于**警告**，可以换颜色提醒：字符串开头写 `\033[` + 色号 + `m`，警告用黄色（`33`），报错才用红色（`31`）；末尾用 `\033[0m` 把颜色改回去，免得影响后面的打印。
```python
# 文件: catalog/core/core.py（接上一节）

def main():
    while True:
        for key in func_dic:
            print(key, func_dic[key][0])          # 打印编号和功能名
        opt = input('请输入功能编号:').strip()
        if opt not in func_dic:
            # \033[33m 开始黄色，\033[0m 恢复默认
            print('\033[33m输入有误，请重新输入\033[0m')
            continue
        func_dic[opt][1]()                        # 取出函数并调用，输入 0 时调用 exit
```

| 颜色 | 前景色号 | 背景色号 |
|---|---|---|
| 红 | 31 | 41 |
| 绿 | 32 | 42 |
| 黄 | 33 | 43 |
| 蓝 | 34 | 44 |

## 10.13 启动文件的位置与相对导入报错

以前会在 `core.py` 里直接调用 `main()`。按目录规范，程序应从 `bin/run.py` 启动，于是要在 `run.py` 里调用 `main`，这就涉及跨文件夹导入。先试相对导入：一个点代表当前文件夹 `bin`，`core` 在 `catalog` 下，所以用两个点跳到上一层：

```python
# 文件: catalog/bin/run.py（错误示范，直接运行会报错）
from ..core.core import main
main()
```

PyCharm 全程给了提示，运行却报错：

```text
ImportError: attempted relative import with no known parent package
```

**原因**：`run.py` 是被**直接运行**的，对它来说顶级包就是 `bin`，而 `..` 想跳出 `bin`，相对导入就失败了。如果 `catalog` 是作为包被导入的，顶级包是 `catalog`，同样写法就不会报错。
**结论：执行文件中只能用绝对导入。**

```python
# 文件: catalog/bin/run.py（第二版：路径写死）
import sys

sys.path.append(r'D:\teach\catalog\core')   # core 文件夹的绝对路径

from core import main

main()
```

这个版本能跑，但有两个问题：

1. **路径写死**：别人的电脑上可能没有 `D:\teach\catalog\core`，一执行就报错
2. **只加了 core**：后面还要导入 `conf`、`db`……有 100 个文件夹就得加 100 次

这些文件夹的共同点是都在 `catalog`（项目根目录）下。所以**只需把项目根目录加入 `sys.path` 一次**：

```python
# 文件: catalog/bin/run.py（第三版：加项目根目录，但仍写死）
import sys

sys.path.append(r'D:\teach\catalog')       # 项目根目录

from core.core import main     # 从 core 文件夹找到 core.py，导入 main
from conf import settings
from db import db_handle

main()
```


:::tip[技巧]
PyCharm 中复制文件绝对路径的快捷键是 `Ctrl+Shift+C`。如果输入法等软件也占用了这个快捷键，要把其他软件的改掉，否则会冲突。
:::

## 10.14 用 `__file__` 动态获取项目根目录

要解决"路径写死"，就得让程序自动算出项目根目录。
每个 Python 文件都有属性 `__file__`，表示**当前文件的绝对路径**。再用 `os.path.dirname()` 取路径的父级文件夹：调用一次得到 `bin`，再调用一次就得到 `catalog`。
```python
# 文件: catalog/bin/run.py（第四版：动态获取根目录）
import os
import sys

# run.py -> bin -> catalog，调用两次 dirname
BASE_DIR = os.path.dirname(os.path.dirname(__file__))
sys.path.append(BASE_DIR)

from core.core import main

if __name__ == '__main__':
    main()
```

这样项目在任何电脑上都能正常运行。最后的 `if __name__ == '__main__':` 加不加都行，但行业里习惯这么写，推荐加上。
单独验证 `dirname` 的效果：

```python
import os

path = r'D:\teach\catalog\bin\run.py'          # 假设这是 __file__
print(os.path.dirname(path))                    # 输出: D:\teach\catalog\bin
print(os.path.dirname(os.path.dirname(path)))   # 输出: D:\teach\catalog
```


:::note[补充]
其他方案：`pathlib` 的 `Path(__file__).resolve().parent.parent`；`os.path` 的更多用法见"常用标准库"一章。
:::

**记录日志的功能**：用户的关键操作（何时登录、注册、充值多少、给谁转了多少钱）要永久保存，写进 `log` 文件夹下的文件。用 `at` 模式（追加写文本，见文件操作一章）打开，编码 `utf-8`，内容由调用者通过参数 `message` 传入，每条带上时间。
```python
# 文件: catalog/core/core.py 中增加（第一版：路径写死）
import time

def logger(message):
    with open(r'D:\teach\catalog\log\user.log', mode='at', encoding='utf-8') as f:
        f.write(f'{time.strftime("%Y-%m-%d %H:%M:%S")} {message}\n')
```

| 格式符 | 含义 |
|---|---|
| `%Y` | 四位数年份 |
| `%m` | 月份 |
| `%d` | 一个月中的第几天 |
| `%H` | 24 小时制的小时 |
| `%M` | 分钟 |
| `%S` | 秒 |

在各功能里调用（用户名这里先写死，正常应获取当前用户的账号）：

```python
def login():
    print('执行登录功能'.center(30, '*'))
    logger('大仙登录了')

def register():
    print('执行注册功能'.center(30, '*'))
    logger('大仙注册了')

def recharge():
    print('执行充值功能'.center(30, '*'))
    logger('大仙充值了100个W')

def transfer():
    print('执行转账功能'.center(30, '*'))
    logger('大仙给李四转了5个亿')
```


:::note[补充]
标准做法是给日志**分类**（登录注册、用户操作、交易日志分开记录），方便后台管理。后面会学专门做日志管理的 `logging` 模块，不会再用手写 `open` 的方式。
:::

### 10.14.1 把公共功能放进 lib

记录日志显然不属于核心逻辑，而且各种操作都可能要用，所以应该剥离出来放进 `lib`。
```python
# 文件: catalog/lib/common.py
import time

from conf.settings import LOG_PATH

def logger(message):
    with open(LOG_PATH, mode='at', encoding='utf-8') as f:
        f.write(f'{time.strftime("%Y-%m-%d %H:%M:%S")} {message}\n')
```

`run.py` 已经把 `catalog` 加入 `sys.path`，这里直接以 `lib` 开头做绝对导入：

```python
# 文件: catalog/core/core.py 开头
from lib.common import logger    # 直接导名字，调用时不用加前缀
# 也可以写 from lib import common，但之后要写 common.logger(...)
```

### 10.14.2 把配置路径放进 settings

日志文件会越来越大，使用者可能想单独拿一块硬盘存日志，所以路径应该放在配置文件里让用户自己配置。配置文件中的变量名用**大写**是规范，**并不表示常量**。
但配置里的路径也不能写死——软件至少应保证**不做任何配置也能直接用**。套路一样：`settings.py` 的 `__file__` 的父级是 `conf`，再父级就是 `catalog`。
```python
# 文件: catalog/conf/settings.py
import os

# settings.py -> conf -> catalog
BASE_DIR = os.path.dirname(os.path.dirname(__file__))

# 日志文件路径（用户可自行修改）
LOG_PATH = os.path.join(BASE_DIR, 'log', 'user.log')
```


:::warning[注意]
不要导入执行文件（`run.py`）里的变量。它是程序入口、是被直接运行的，**即便能导也不要去导它**。
:::

## 10.15 纠错：启动文件放项目根目录

bin 下文件较少时，可以把启动文件直接放项目根目录，删掉 `bin` 文件夹：

```text
catalog/
├── run.py              <- 启动文件移到根目录
├── conf/settings.py    <- BASE_DIR、LOG_PATH
├── core/core.py        <- login/register/recharge/transfer、func_dic、main
├── lib/common.py       <- logger
├── db/db_handle.py     <- 数据操作（本例未使用）
├── log/user.log        <- 运行后自动生成
├── requirements.txt
└── README.md
```

启动文件在根目录时，`sys.path[0]` 就是根目录，**不需要再计算 `BASE_DIR` 并加入 `sys.path`**，代码大为精简：

```python
# 文件: catalog/run.py（放在项目根目录）
from core.core import main

if __name__ == '__main__':
    main()
```

运行后输入 1~4、0 都正常，日志文件也新增了记录。

:::warning[注意]
网上流传"启动文件必须放在 bin 下"，这不准确。执行文件放 `bin` 下还是放根目录都可以，**没有绝对的应该或不应该**——放 `bin` 下需要手动把项目根目录加入 `sys.path`，放根目录则天然满足。按项目的规模和团队约定来即可。
:::

## 本章小结

- **模块**是一系列功能的集合体，一个 `.py` 文件就是一个模块；分内置、第三方、自定义三类。
- **首次导入模块**会执行一遍文件、产生模块名称空间、在当前文件产生指向它的名字；重复导入只引用首次结果（已导入模块记录在 `sys.modules` 里）。
- **名称空间查找顺序在定义阶段确定**：模块中的函数查找、修改的都是模块自己的名字，与调用位置无关。
- **导入规范**：分行导入，按内置 → 第三方 → 自定义的顺序；模块名用纯小写加下划线；`as` 起别名。
- **`__name__`**：直接运行为 `'__main__'`，被导入为模块名；测试代码写在 `if __name__ == '__main__':` 下。
- **`from module import name`**：名字直接指向值，不用前缀但易冲突；`*` 慎用，可用 `__all__` 控制（默认导入所有不以下划线开头的名字）。
- **循环导入**是设计问题，应从一开始就避免；补救办法是把名字定义提前，或把用到的代码缩进到函数里。
- **包**是含有 `__init__.py` 的文件夹，也是模块的一种；**导包执行的就是 `__init__.py`**。
- **包的意义**：设计者把功能拆到多个文件便于维护，同时用 `__init__.py` 汇总名字，对使用者屏蔽内部变化、保持用法不变。
- **被导入模块的 `sys.path` 参照执行文件的 `sys.path`**，所以包内绝对导入必须从顶级包开始写，前提是使用者把包所在路径加入 `sys.path`。
- **导入时点的左边必须是包**；`import game.chat` 后使用时必须带完整前缀，不推荐。
- **相对导入**用 `.`（当前文件夹）、`..`（上一层），不能跳出顶级包，仅限包内使用；包内推荐相对导入（层级短、改包名不用改代码）。
- **目录规范**：`bin` 放执行文件、`conf` 放配置、`lib` 放公共功能、`core` 放核心逻辑、`log` 放日志、`db` 放数据操作，另有 `requirements.txt`（外部依赖，文件名不可改）和 `README.md`（说明文档，一定要有）。
- **执行文件中不能用相对导入跳出顶级包**（报 `ImportError: attempted relative import with no known parent package`），应改用绝对导入。
- 把**项目根目录加入 `sys.path` 一次**即可，用 `os.path.dirname(os.path.dirname(__file__))` 动态获取，避免路径写死。
- 公共功能放 `lib`；可配置的路径放 `conf/settings.py`，变量名大写并动态计算默认值；不要导入执行文件里的变量。
- 启动文件放项目根目录时 `sys.path[0]` 就是根目录，无需再处理环境变量。
